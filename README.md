# galentinesglobal.com

Next.js (Pages Router) site for Galentines, with [Payload CMS](https://payloadcms.com) embedded for content editing at `/admin`.

## Local development

1. `cp .env.example .env` and fill in:
   - `DATABASE_URL`: a Postgres database **used only for local dev** (e.g. a dev branch of the Neon database). Never point local dev at production; see [Migrations](#migrations).
   - `PAYLOAD_SECRET`: `openssl rand -hex 32`
   - `BLOB_READ_WRITE_TOKEN`: optional. When empty, uploads are stored in `./media`.
2. `npm install`
3. `npm run dev`, then open `http://localhost:3000/admin` to create the first admin user.

## Project layout

- `payload.config.ts`: Payload config (Postgres, Vercel Blob storage, Lexical editor)
- `collections/`: Payload collections (`users`, `media`)
- `app/(payload)/`: Payload admin and API routes (App Router). Generated by Payload; don't edit by hand.
- `pages/`: the public site (Pages Router)
- `payload-types.ts`: generated types. Run `npm run generate:types` after changing collections.
- `migrations/`: database migrations applied in production

## Migrations

In dev, Payload pushes schema changes straight to the database. Production only applies committed migrations, which run automatically when the server starts (`prodMigrations` in `payload.config.ts`). After changing a collection's fields:

```bash
npx payload migrate:create <name>
```

Commit the generated files in `migrations/`. Payload refuses to run migrations against a database that dev mode has already pushed to, which is why local dev and production must use separate databases.

## Deploying (Vercel)

The Vercel project needs:

- **Neon Postgres** (Vercel Marketplace). This sets `DATABASE_URL`. Enable preview branching so preview deploys get their own database branch.
- **Vercel Blob** store. This sets `BLOB_READ_WRITE_TOKEN`.
- `PAYLOAD_SECRET`: a different random value per environment.
